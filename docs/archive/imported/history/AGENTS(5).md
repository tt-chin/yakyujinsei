# YaKyoLife 開発ルール

このファイルはリポジトリ全体に適用する恒久ルールです。個別タスクの詳細は、指定された `tasks/*.md` も併せて確認してください。

## 1. 作業開始前

- 現行の `docs/index.html`、`YaKyoLife_詳細設計書.md`、およびユーザーが指定したタスク文書を最初に最後まで読む。
- 既存のユーザー変更を保持し、依頼範囲外の修正を混ぜない。
- 仕様間の矛盾、参照ファイルの不足、再現不能な条件があれば、推測で実装せず報告する。
- 明示的な承認が必要と書かれた工程では、承認前にファイルを変更しない。

## 2. 既存仕様との互換性

- 現行正式バージョンのゲーム内容、表示文、翻訳、画面構成、DOM順序、条件分岐、イベント順序は、個別タスクで変更対象として指定されていない限り変更しない。
- 能力値、リーグ基準、成績生成、成長・衰退、故障、年俸、契約、移籍、賞、引退、殿堂入りの挙動を保持する。
- 乱数アルゴリズム、乱数呼び出し順、乱数消費回数を保持する。同一seedで結果が変わる変更は、ユーザーの明示的承認なしに行わない。
- 旧台湾版や将来版の機能は、個別タスクで明示された場合を除き取り込まない。
- 内部識別子 `VERSION` は固定値として扱わず、本ファイルの「バージョン管理と更新履歴」ルールに従って更新する。

## 3. 共有URL

- 共有URLはseed-only方式とし、クエリは `?seed=<SEED>` のみ生成する。
- URLに `rv`、`rules`、固定ドメインを追加しない。
- 旧URLに `rv` や `rules` が含まれていてもseedだけを読み、現行正式バージョンとして開始する。
- `UNSUPPORTED_REPLAY_VERSION` や旧エンジン切替を復活させない。
- ゲーム更新後に過去と完全同一の人生を保証する二重互換モードは設けない。

## 4. 日本語と翻訳

- 日本版の画面文言は自然な日本語を基本とし、指定がある場合は5ちゃんねる等で通用する日本のネット用語を使う。
- 中国語に対応する自然な日本語・ネット用語が存在しない場合は、無理に造語せず空欄候補として明示し、ユーザーに報告する。
- 承認済みの固有表現、称号、表示文を独断で言い換えない。

## 5. 構成と配信

- GitHub Pagesから静的配信できる構成を維持する。
- ユーザーの承認なしにビルドツール、npm依存、フレームワーク、サーバー処理を導入しない。
- ファイル参照は相対パス、文字コードはUTF-8を使用する。
- モジュール化では実在する責務に対応するファイルだけを作成し、空ファイルや不要な抽象化を作らない。
- 既存の状態オブジェクト `S` は、必要性と互換性を確認せず全面再設計しない。

## 6. 変更と検証

- 変更前に対象範囲と依存関係を確認し、小さく追跡可能な単位で編集する。
- 構文、import/export、相対パス、404、コンソールエラーを検証する。
- ゲームロジック変更または構造変更では、投手・野手の固定seed回帰テストを行い、乱数消費回数を含めて比較する。
- PC・モバイルで主要フローを確認し、開始、選択、シーズン進行、引退、結果画像、URLコピーを可能な範囲で実動確認する。
- 実行環境の制約で未確認項目が残る場合、確認済みと偽らず最終報告に列挙する。
- 実装後は関連する設計書を更新し、コードと仕様の不一致を残さない。

## 7. Gitと安全性

- `git reset --hard`、無断削除、既存変更の破棄などの破壊的操作を行わない。
- 関係のないファイルを整形・改名・移動しない。
- 秘密情報や環境固有の絶対パスをコードへ埋め込まない。

## 8. 指示の優先順位

- ユーザーの最新の明示指示を最優先する。
- 個別タスク文書はそのタスクの範囲・手順を補足するが、この文書の安全性および互換性ルールを暗黙に解除しない。
- 指示が衝突する場合は作業を止め、衝突箇所と選択肢を提示する。

## 9. バージョン管理と更新履歴

### 9.1 バージョン形式

- ゲームの正式バージョンは `x.x.x` 形式で管理する。
- バージョン番号は `MAJOR.MINOR.PATCH` の3桁とする。
- 実装作業を開始する前に、必ずリポジトリ内から現在の正式バージョン番号と、そのバージョンを管理しているファイルを確認する。
- 複数箇所でバージョン番号を保持している場合は、更新漏れによる不一致を残さない。

### 9.2 バージョンアップ基準

以下の一般ルールを使用して、変更内容から次のバージョン番号を判断する。

#### PATCH：`x.x.Z → x.x.(Z+1)`

既存仕様の範囲内での修正はPATCHとする。

例：

- バグ修正
- 表示崩れの修正
- UIの軽微な修正
- 誤字・翻訳・文言の修正
- 計算式や条件分岐の不具合修正
- 既存機能が仕様どおり動いていなかった問題の修正
- 既存仕様を変更しない軽微なデータ修正
- パフォーマンス改善

例：
`1.0.8 → 1.0.9`

#### MINOR：`x.Y.z → x.(Y+1).0`

後方互換性を基本的に維持したまま、ユーザーが認識できる新機能・新システム・仕様拡張を追加する場合はMINORとする。

例：

- 新しいゲームシステム
- 新しいリーグ・進路・大会
- 新しいイベント種別
- 新しい画面・操作機能
- 既存システムへの大きな機能追加
- ゲームバランスやルールの明確な仕様変更
- ユーザー体験に影響する比較的大きな仕様拡張

MINORを上げる場合、PATCHは0へ戻す。

例：
`1.0.9 → 1.1.0`

#### MAJOR：`X.y.z → (X+1).0.0`

既存バージョンとの互換性を維持できない大規模変更、またはゲームの根幹を変更する大型アップデートの場合はMAJORとする。

例：

- セーブ・共有データとの互換性を失う大規模変更
- ゲーム進行構造の全面変更
- コアゲームシステムの全面刷新
- 既存仕様を大幅に破壊する変更
- 大規模なデータ構造変更

MAJORを上げる場合、MINORとPATCHは0へ戻す。

例：
`1.9.4 → 2.0.0`

### 9.3 バージョンアップ不要の変更

以下のみの変更で、ゲームの実際の動作・表示・配信内容に影響しない場合は、原則としてバージョン番号を変更しない。

- 設計書・README・AGENTS.mdなどの文書のみの変更
- コメントのみの変更
- テストコードのみの追加・修正
- 実際の挙動を変えない内部リファクタリング
- 開発用ツール・開発手順のみの変更

ただし、これらと同時にゲーム本体を変更した場合は、ゲーム本体の変更内容に従ってPATCH・MINOR・MAJORを判断する。

### 9.4 実装時の必須手順

ゲーム本体に変更を加えるすべてのタスクで、以下を必ず実施する。

1. 作業開始前に現在の正式バージョンを確認する。
2. 実装内容を確認し、PATCH・MINOR・MAJORのどれに該当するか判断する。
3. 実装とテストが完了した後、適切な次バージョンへ更新する。
4. リポジトリ内でバージョン番号を管理しているすべての正式な箇所を更新する。
5. バージョン番号更新と同じタスク内で、必ずバージョン更新履歴を更新する。
6. コード、画面表示、設計書、更新履歴のバージョン番号に不一致がないことを確認する。

バージョン番号だけを変更して更新履歴を追加しないことを禁止する。

更新履歴だけを追加して正式バージョン番号を変更し忘れることも禁止する。

### 9.5 バージョン更新履歴

- 正式なバージョン更新履歴は、リポジトリ内の `VERSION_HISTORY.md` で管理する。
- バージョン番号を更新した場合は、同一タスク内で必ず `VERSION_HISTORY.md` に新しいバージョンの更新履歴を追加する。
- 別のバージョン履歴ファイルを新規作成してはならない。
- `VERSION_HISTORY.md` の既存フォーマット、記載順序、表記方法を確認し、その形式を維持して追記する。
- 原則として最新バージョンを既存履歴の規則に従った位置へ追加する。
- 更新履歴には、実際にそのバージョンで実装・修正された内容だけを記載する。
- 未実装、予定、検討中、推測の内容を更新履歴へ記載してはならない。

更新履歴には最低限、以下を記載する。

- バージョン番号
- 変更内容
- 修正した主要バグ
- 新機能または仕様変更（存在する場合）

必要に応じて以下も記載する。

- UI変更
- ゲームバランス変更
- データ変更
- 互換性への影響
- 移行上の注意

バージョン番号だけを更新して `VERSION_HISTORY.md` を更新しないことを禁止する。

`VERSION_HISTORY.md` だけを更新して、正式なバージョン番号を更新し忘れることも禁止する。

### 9.6 同一タスクに複数変更がある場合

1つのタスクまたは1回のリリースに複数の変更が含まれる場合、変更ごとに個別のバージョンを付けない。

そのリリースに含まれる変更のうち、最も大きい変更区分を採用する。

例：

- バグ修正 + 文言修正 → PATCH
- 新機能 + バグ修正 → MINOR
- 互換性を破壊する変更 + 新機能 + バグ修正 → MAJOR

### 9.7 判断に迷う場合

PATCH・MINOR・MAJORの判断が明確でない場合、独断で大きなバージョンアップを行わない。

既存機能を本来の仕様へ戻す修正は原則PATCHとする。

新しい仕様・新しいユーザー向け機能を追加する場合は原則MINORとする。

互換性を意図的に破壊する変更のみMAJOR候補とする。

それでも判断できない場合は、実装前またはバージョン更新前にユーザーへ確認する。

### 9.8 最終報告

バージョンを更新したタスクでは、最終報告に必ず以下を含める。

- 変更前バージョン
- 変更後バージョン
- PATCH / MINOR / MAJOR のどれを適用したか
- その区分を選択した理由
- バージョン番号を更新したファイル
- バージョン更新履歴を追加したファイル
- 更新履歴へ追加した内容の概要

## 10. ブランチ運用・Cloudflare Preview・本番反映

### 10.1 基本方針

- 通常の修正、機能追加、UI変更、バグ修正は `main` に直接コミットまたは push しない。
- 開発・確認用ブランチとして `dev` を使用する。
- 作業開始前に `main` の最新状態を確認し、必要に応じて `dev` に反映してから作業する。
- 修正完了後は原則として `dev` に commit / push する。
- ユーザーが Preview 確認OKを出すまでは、`main` へ merge / push しない。
- ユーザーが「本番反映」「mainへ反映」等を明示した場合のみ、確認済みの `dev` の内容を `main` に反映する。

### 10.2 Cloudflare Pages Preview

- `dev` は Cloudflare Pages の Preview 用ブランチとする。
- `dev` への push 後は Cloudflare Pages の自動デプロイ対象となる。
- 固定 Preview URL は `https://dev.yakyujinsei.pages.dev` とする。
- ユーザーは原則としてこの Preview URL で PC・モバイルの実動確認を行う。
- commit ごとの一時的な deployment URL が生成されても、通常の確認案内では固定 Preview URL を優先する。
- Cloudflare Pages の Production branch は `main` のまま維持する。
- ユーザーの明示的承認なしに Cloudflare Pages の Custom Domain、Production branch、Preview branch、Build 設定を変更しない。
- Cloudflare Pages を `yakyujinsei.com` の本番配信元へ切り替えない。

### 10.3 本番公開フロー

- 開発元リポジトリは `tt-chin/yakyujinsei` とする。
- `main` 更新後の本番公開は、既存 GitHub Actions Workflow により公開用リポジトリ `tt-chin/yakyujinsei-site` へ同期する既存方式を維持する。
- 本番サイトは `yakyujinsei.com` とする。
- `yakyujinsei-site` を通常の開発作業先として直接編集・直接開発しない。
- ユーザーの明示的承認なしに、`yakyujinsei` → `yakyujinsei-site` の既存同期 Workflow を変更、削除、置換しない。
- Cloudflare Preview 導入を理由に既存の本番公開フローを変更しない。

### 10.4 禁止事項

以下はユーザーの明示的指示がない限り禁止する。

- `main` への無断直接コミットまたは push
- Preview 確認前の `dev` → `main` 反映
- `yakyujinsei-site` への直接開発
- Cloudflare Pages を本番サイトへ切り替える変更
- Cloudflare Pages の Custom Domain 設定変更
- Cloudflare Pages の Production branch / Preview branch の無断変更
- 既存 GitHub Actions Workflow の不要な変更
- Preview 用の変更を本番用ファイルへ意図せず混入させること

### 10.5 標準開発フロー

通常の開発・修正は以下の順序で行う。

1. `main` の最新状態を確認する。
2. `dev` を最新の `main` に追従させる。
3. `dev` 上で実装・修正を行う。
4. 必要なテストを実施する。
5. `dev` に commit / push する。
6. Cloudflare Pages の自動 Preview deployment が完了したことを確認する。
7. `https://dev.yakyujinsei.pages.dev` をユーザーへ Preview 確認URLとして案内する。
8. ユーザーによる実動確認を待つ。
9. 修正指示がある場合は `dev` 上で追加修正し、再度 Preview 確認を行う。
10. ユーザーが明示的に本番反映を承認した場合のみ、確認済みの内容を `main` に反映する。
11. `main` 更新後は既存 GitHub Actions Workflow による `yakyujinsei-site` への同期を利用する。
12. 本番サイト `yakyujinsei.com` への反映結果を確認する。

Preview 確認と本番反映を同一工程として扱わないこと。

### 10.6 作業完了時の報告

`dev` で実装・修正を行った場合、最終報告に最低限以下を含める。

- 使用したブランチ
- 修正したファイル
- commit SHA
- push 先
- Preview 確認URL（原則 `https://dev.yakyujinsei.pages.dev`）
- `main` を変更していないこと
- 実施したテストと結果
- 未確認項目がある場合はその内容
- ユーザーによる Preview 確認後に `main` へ反映すべき状態かどうか

ユーザーから本番反映を明示的に指示された場合は、以下も報告する。

- `main` への反映結果
- `main` の commit SHA
- 既存 Workflow の実行結果（確認可能な範囲）
- `yakyujinsei-site` への同期結果（確認可能な範囲）
- 本番サイトへの反映確認結果
- 確認できなかった項目がある場合はその理由

### 10.7 文書のみの変更

- 本章の追加・更新など `AGENTS.md` のみを変更する場合は、第9.5節に従いゲームのバージョン番号を変更しない。
- Cloudflare Preview、Git ブランチ運用、開発手順のみの変更も、ゲーム本体の動作・表示・配信内容を変更しない限りバージョンアップ対象外とする。
