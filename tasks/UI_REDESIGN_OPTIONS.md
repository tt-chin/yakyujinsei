# UI 改版選項（RPG／大富翁風格）

狀態（2026-11-13）：**提案，待 code owner 決定方向**。非現行規格，不授權實作；`CURRENT_SPEC.md` 與 `BACKLOG.md` 未變更，方向決定後再登記 BACKLOG 項目並寫細部計畫。

- 前提（使用者 2026-11-13）：新風格**取代**現有介面，不與現有 4 主題並存切換。
- 本文對現有畫面的描述，依據 2026-11-12～13 作業中看過的程式碼（`docs/src/ui/*`、`docs/styles/*`、`docs/src/engine/game.js` 的繪製部分），未另做全面盤點；各項細部計畫時須重新盤點。
- 分級依 AGENTS §6.1（R0～R3），版本區分依 §9.2，皆為預估，細部計畫時重判。

## 0. 三種程度

| 程度 | 內容 | 遊戲規則／RNG | 預估分級 | 預估版本 |
|---|---|---|---|---|
| A | 只換外觀（CSS 模板） | 不變 | R2 | PATCH～MINOR |
| B | 新的呈現方式（同一份資料換畫面） | 不變 | R2（觸及事件順序者 R3） | MINOR |
| C | 改玩法 | 依項目而定（逐項判斷，§3） | R2～R3 | MINOR～MAJOR |

## 1. A：只換外觀

版面、DOM 順序、操作流程、顯示文字皆不變，只換 CSS 模板。

| # | 選項 | 內容 |
|---|---|---|
| A1 | 像素 RPG 風 | 點陣字體（須含日文字形）、深底白框的「視窗」面板、按鈕前加 ▶ 游標 |
| A2 | 冒險手帳風 | 羊皮紙紋理、墨水色、印章樣式的稱號與特性標籤 |
| A3 | 桌遊／大富翁風 | 紙鈔色系、棋盤格底紋、地契卡／機會卡外框、金額以鈔票樣式顯示 |
| A4 | 背景 | 現行球場背景（`stadium-background.css`）換成原野、城鎮或棋盤 |
| A5 | 圖示 | 以 CSS／SVG 在既有文字旁加圖示（劍、盾、金幣），DOM 不變 |
| A6 | 分享圖 PNG | 配色已可隨主題（UI-DESIGN-TOKENS-03）；字體跟隨新風格須 P4 |

- 前置：設計系統計畫 P3（UI-DESIGN-TOKENS-05，語意色＋推導）與 P4（UI-DESIGN-TOKENS-06，字體、字級、圓角、陰影、間距）。完成後新風格即一套模板。
- 限制：只靠 CSS，「看起來像 RPG」，操作仍是現行按鈕與表格。

## 2. B：新的呈現方式

遊戲規則與 RNG 不變，以新畫面呈現現有資料。

| # | 選項 | 內容 |
|---|---|---|
| B1 | RPG 狀態視窗 | 能力值改量條；年齡或年資對應 Lv、守位對應「職業」、特性對應「技能」 |
| B2 | 成長演出 | 能力上升時「レベルアップ！」與數字跳動 |
| B3 | 對話式事件 | 文字逐字顯示、NPC 頭像（監督、記者、家人）、選項以游標選單呈現，可鍵盤操作 |
| B4 | 大富翁式生涯棋盤 | 一格＝一個年度或階段（高校→大學→社會人→職業→引退），棋子標示目前位置，走過的格子顯示當年成績；生涯回顧為走完的棋盤 |
| B5 | 機會卡／命運卡 | 隨機事件以翻卡呈現；結果已由 RNG 決定，翻卡只是演出 |
| B6 | 世界地圖 | 移籍、聯盟（NPB、KBO、CPBL、MLB）以地圖呈現 |
| B7 | 資產表 | 年俸與收入以大富翁式資產表、鈔票呈現 |
| B8 | 結局 | 引退與殿堂改為 RPG 式片尾名單與稱號獲得畫面 |
| B9 | 音效／BGM | Web Audio，靜態配信可行；素材須原創或取得授權 |

- 限制：
  - 畫面已分散於 `GameView`（`game-view.js`）、`CareerPresenter`（`career-presenter.js`）、`ChoicePrompt`（`choice-prompt.js`）、`ShareImage`（`share-image.js`）等模組，部分仍經 `game.js`；細部計畫須以最新模組重新確認各畫面的生成位置，並逐項確認測試耦合（部分測試以原始碼文字掛鉤 `game.js`），不依舊架構把程式搬回 `game.js`（§7.3）。
  - 演出不得呼叫 `R`，否則同 seed 結果改變（AGENTS §2）。
  - DOM 快照類 e2e（如 `game-view-dom-e2e`）須更新期待值，屬畫面規格變更，須核准。
- 按可獨立驗收的完整畫面或互動範圍分批 PR，不必每個小效果各一個；每批列明允許的顯示差異，保留狀態、選擇與 RNG 的相關斷言（§7.2）。

## 3. C：改玩法

| # | 選項 | 內容 |
|---|---|---|
| C1 | 擲骰前進 | 每季或每年擲骰，停留格觸發練習、比賽或事件（大富翁核心） |
| C2 | 資產經營 | 買球場、贊助、投資、收租；改寫現行年俸與收入系統 |
| C3 | 回合制對決 | 打席／投球對決改為指令戰鬥（揮棒、觸擊、選球） |
| C4 | 探索地圖與商店 | 在城鎮與球場間移動，遇 NPC 觸發事件，購買球棒、手套等裝備加能力 |
| C5 | 經驗值與技能樹 | 取代現行能力分配 |
| C6 | 任務系統 | 主線（甲子園→選秀→殿堂）與支線 |
| C7 | 多人輪流 | 無伺服器，僅能同一裝置輪流 |

- 影響須逐項判斷（§7.3）：依是否新增決策或抽選、改變事件順序或資料處理，判定 R 分類、允許差異與版本。
  - 不新增抽選者（例：C6 僅依現有實績顯示任務進度）可能不改變 RNG 與 seed 結果。
  - 新增抽選或決策者（例：C1 擲骰、C3 指令戰鬥、C4 探索）改變 RNG 呼叫順序與次數，同 seed 產生不同人生；舊分享網址仍可開啟但結果不同，AGENTS §3 禁止舊引擎切換與完全重現用的二重互換模式，舊人生無法重現；固定 seed 回歸、golden、殿堂平衡研究、`CURRENT_SPEC.md` 須重做，版本可能為 MAJOR。
- C1～C4 合併實施時，實質上為新遊戲。

## 4. 「取代現有介面」的連帶影響

| 項目 | 內容 |
|---|---|
| 主題 | 現行 4 主題（standard、night、classic、scoreboard）是否移除；模板機制（P2～P4）仍可沿用，新風格本身為一套模板，可保留其明暗兩種變化 |
| 顯示文字 | 已核准的日文表示文、稱號（AGENTS §4）：A 原樣保留；B、C 若改措辭須逐項核准 |
| 測試基準 | 分享圖與 1.11.0 的像素比較（`replay-share-theme-e2e`）、DOM 快照、凍結檔的核准 overlay（`award-identity-policy.test`），期待值須重新核准 |
| 可讀性 | 點陣字體在長篇日文、320px 寬手機上的可讀性須實測 |
| 素材 | 頭像、地圖、像素圖須原創；可參考 RPG／桌遊類型，不得照搬特定遊戲的名稱、角色、美術或外觀 |
| 配信 | 維持靜態配信，不引入建置工具、npm 依賴或框架（AGENTS §5） |

## 5. 建議

- 取代介面且不破壞既有 seed：A＋部分 B（建議 B1、B3、B4、B2），可得大部分 RPG／大富翁感。順序：P2（UI-DESIGN-TOKENS-04）→ P3 → P4 → 新風格模板（A）→ B 逐項。
- C 須逐項判斷影響；會改變 RNG 的項目（C1～C4 等）須先決定是否接受舊 seed 與舊分享連結結果改變，再談細節。

## 6. 待 code owner 決定

1. 程度：A／A＋B／C。
2. 風格：A1～A3 中的哪一種（或混合，例如 RPG 視窗＋大富翁棋盤）。
3. B、C 中要做的項目與優先順序。
4. 現行 4 主題移除或保留為變化。
5. 選會改變 RNG 的 C 項時：是否接受舊 seed／分享連結結果改變，與版本（可能 2.0.0）的發布方式。


## 7. Codex 補充看法（2026-11-13，供方向討論）

以下為設計建議，尚未經 code owner 選定，不取代第6節的待決事項，也不構成產品實作或規則修改授權。

### 7.1 推薦方向：棒球選手手帳＋RPG成長感

建議採A2＋部分B，先保留現行玩法。視覺以球員卡、球探報告、成績單、冠軍印章建立棒球特色，RPG元素用於成長與特性呈現。球場照片可保留，不必為了RPG風格換成原野或城鎮；也不必加入與棒球無關的劍、盾或金幣。單純套像素框的改善有限，加入擲骰走格則涉及另一層玩法決策，應分開討論。

- **能力／特性（B1）：** 能力量條同時顯示目前值與潛力，特性以徽章呈現；保留「年齢」「守備位置」等棒球用語，不把年齡直接改叫Lv，以免被理解為另一套等級或成長規則。正文與數字以易讀字體為主，像素字體如採用，可先限於標題或裝飾。
- **首頁與事件（B3）：** 突出目前事件及接下來的選擇，過往紀錄收進年度區塊。手機減少在事件與選項間往返捲動；桌面沿用左側能力、中間事件、右側成績／契約的空間配置。
- **生涯路線圖（B4）：** 依實際經歷標出升學、入團、轉隊、受傷與獲獎，點選節點查看當年紀錄。這是已發生生涯的視覺化，不額外擲骰，不強迫所有人走固定升學路線，也不從不足的舊資料補造經歷。
- **成長與得獎演出（B2／B5）：** 動畫保持簡短、可略過；逐字文字、翻卡與音效可關閉。顯示演出不得新增抽選，不讓動畫等待成為遊戲處理的必要條件；重複操作、跳過、離開畫面及舊callback仍須安全。
- **退休與分享圖（B8）：** 與新介面使用一致的字體、配色及資訊層級，保留成績、收入、稱號與授權資訊的可讀性。BGM、世界地圖、完整NPC頭像可在核心畫面定案後再做。

### 7.2 建議優先順序

1. 整體視覺、文字可讀性與資訊層級。
2. 能力／特性頁及事件選項。
3. 生涯年度路線圖。
4. 退休畫面與分享圖。
5. 視需要追加音效、地圖與頭像素材。

不必機械式地每個小效果各拆一個PR；可按可獨立驗收的完整畫面或互動範圍分批。每批仍須列明允許的顯示差異，保留狀態、選擇與RNG的相關斷言，不因介面改版而整份略過歷史比較。

### 7.3 細部計畫前應補強的說明

- **以最新模組為準：** 第2節「多數畫面在game.js內產生」不宜直接當作實作依據。目前已有GameView、CareerPresenter、ChoicePrompt與ShareImage等模組；細部計畫應重新確認各畫面的生成位置與測試耦合，不依舊架構搬回程式。
- **逐項判斷C的影響：** C並非每一項必然改變全部RNG或所有seed結果。例如僅依現有實績顯示任務進度，可能不新增抽選。應按實際是否新增決策、改變事件順序或資料處理，判定R分類、允許差異與版本；不能先將所有C項一律視為相同影響。
- **舊主題設定的相容性：** 取代四主題時，須定義舊主題設定如何轉入新介面、字級設定是否保留，以及分享圖如何一致呈現。這是顯示設定的遷移，不應刪除或重建玩家的生涯存檔。新介面是否提供明暗變化，仍待code owner決定。
- **設計稿可先行：** 正式實作仍沿用已批准的設計系統路線；靜態設計稿與可讀性確認可先進行，不必等P2～P4全部完成才確認風格，避免模板完成後才發現畫面方向不合適。設計稿不接入正式遊戲，也不代表批准實作。

### 7.4 建議下一步

以相同的遊戲資料，先製作「首頁、事件選擇、能力頁」的手機與桌面靜態設計稿，確認風格、資訊優先順序及操作距離，再選定要實作的B項、範圍與驗收條件。此步僅為後續建議，本次只追加本文。
